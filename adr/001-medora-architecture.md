# ADR-001. Выбор клиент-серверной архитектуры веб-приложения Medora

## Контекст и постановка задачи

Для веб-приложения **Medora** необходимо реализовать учёт приёма лекарств: справочник препаратов, расписание, отметки приёма/пропуска, напоминания, учёт остатков и историю. После второго раунда согласования в первую версию добавлен режим опекуна (`REQ-FUNC-010`): доверенное лицо получает доступ к расписанию подопечного и уведомлениям о пропущенных дозах.

Требуется выбрать архитектуру, которая разделит отображение, бизнес-правила и хранение данных, обеспечит изоляцию персональных данных и позволит добавлять функции (включая делегированный доступ) без полной переработки системы.

## Драйверы решения

* Реализация требований SRS: `REQ-FUNC-001`–`REQ-FUNC-010`, `REQ-SEC-*`, `REQ-REL-*`.
* Ограничение продукта: серверная часть на Java (Spring Boot), данные в реляционной СУБД.
* Централизованные правила списания остатков и идемпотентности отметок.
* Возможность развивать модули (расписание, уведомления, опекун) независимо.
* Ограниченные сроки и бюджет учебного проекта.
* Тестируемость клиентской и серверной логики по отдельности.

## Рассмотренные варианты

* Клиент–сервер: веб-UI + Spring Boot REST API + PostgreSQL.
* Монолитное приложение только с server-side templates без явного API.
* Полностью клиентское приложение с хранением данных в браузере.

## Итог решения

Выбран вариант **«Клиент–сервер: веб-UI, Spring Boot API и PostgreSQL»**. Клиент отвечает за экраны «Сегодня» и «Карточка лекарства», отметки и отображение уведомлений. Сервер аутентифицирует пользователей, применяет бизнес-правила расписания/остатков/опекунского доступа и сохраняет данные в PostgreSQL. Обмен — HTTP + JSON.

Такое разделение позволяет независимо менять UI и логику, централизовать проверки авторизации (включая `CaregiverLink`) и соответствовать ограничениям SRS по стеку.

### Последствия

* Хорошо, потому что UI и бизнес-логику можно разрабатывать и тестировать раздельно.
* Хорошо, потому что PostgreSQL поддерживает связи сущностей и транзакции для идемпотентных отметок.
* Хорошо, потому что режим опекуна добавляется как слой авторизации на API без смены общей архитектуры.
* Хорошо, потому что стек совпадает с уже согласованным в SRS.
* Плохо, потому что нужно проектировать и сопровождать контракт API.
* Плохо, потому что для работы с данными обычно требуется сеть.
* Плохо, потому что развёртывание включает приложение и СУБД.

### Подтверждение

При реализации: UI не обращается к БД напрямую; все операции с персональными данными требуют аутентификации; повторная отметка дозы не списывает остаток дважды; запросы опекуна проходят только при `ACTIVE` связи. Проверка — код-ревью, API/integration-тесты, сценарии Dashboard/Medicine Card.

## Плюсы и минусы вариантов

### Клиент–сервер: веб-UI, Spring Boot API и PostgreSQL

* Хорошо, потому что разделены представление, логика и хранение.
* Хорошо, потому что соответствует ограничениям SRS (Java, РСУБД).
* Хорошо, потому что архитектура допускает постепенное добавление функций.
* Плохо, потому что необходим согласованный API-контракт.
* Плохо, потому что развёртывание сложнее, чем у чисто клиентского варианта.

### Монолит только с server-side templates

* Хорошо, потому что единая кодовая база может упростить старт.
* Хорошо, потому что логика и доступ к данным в одном приложении.
* Нейтрально, потому что PostgreSQL также применима.
* Плохо, потому что сильнее связывает UI и серверные изменения.
* Плохо, потому что сложнее выделить отдельный клиент/будущий мобильный доступ.

### Полностью клиентское приложение (данные в браузере)

* Хорошо, потому что не нужен собственный backend для базовых действий.
* Хорошо, потому что проще разместить статический UI.
* Плохо, потому что данные зависят от устройства и браузера.
* Плохо, потому что режим опекуна и централизованные уведомления практически невозможны без сервера.
* Плохо, потому что противоречит требованиям изоляции и сохранности (`REQ-FUNC-009`, `REQ-REL-001`).
