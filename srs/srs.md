## 1. Введение {#1-introduction}

Документ SRS описывает требования к веб-приложению **Medora** — системе учёта приёма лекарств. Спецификация фиксирует назначение продукта, границы MVP, функциональные и нефункциональные требования, а также способы их верификации. Целевая аудитория документа — заказчик, команда разработки, QA и преподаватель дисциплины ЖЦРПО.

### 1.1 Назначение документа {#11-document-purpose}

Данный SRS определяет **что** должна делать система Medora, а не как именно она будет реализована внутри. Документ используется разработчиками для проектирования и реализации, тестировщиками — для построения тест-кейсов, заказчиком — для согласования объёма MVP. Связанные артефакты: структурные диаграммы экранов SysML v2 (приложение к отчёту ЛР3), история изменений в Git.

### 1.2 Область применения продукта {#12-product-scope}

**Medora** — веб-приложение для персонального учёта приёма лекарств (версия MVP 0.2). Продукт помогает пользователю вести расписание приёма, получать напоминания, учитывать остатки препаратов, просматривать историю приёма и получать уведомления о пропущенных дозах. По согласованию ЛР4 в MVP также входит ограниченный режим опекуна.

**Входит в MVP:**
- регистрация/вход пользователя;
- справочник лекарств пользователя (название, дозировка, форма);
- расписание приёма (время, дни, периодичность);
- отметка о приёме / пропуске дозы;
- учёт остатков (количество единиц, порог «заканчивается»);
- история приёма с фильтрацией по дате и препарату;
- напоминания и уведомления о пропущенных дозах (в веб-интерфейсе и/или через браузерные Web Push при наличии разрешения);
- режим опекуна: приглашение доверенного лица, просмотр расписания подопечного и получение уведомлений о пропущенных дозах.

**Не входит в MVP:**
- электронные рецепты и интеграция с аптеками/страховыми;
- телемедицина и консультации врача;
- нативные мобильные приложения (iOS/Android);
- AI-рекомендации по лечению и дозировкам;
- email/SMS-напоминания (отложено после раунда 1 согласования);
- полноценный семейный кабинет с расширенными ролями и правами редактирования чужих данных (сверх ограниченного режима опекуна).

Бизнес-цель: снизить число пропущенных приёмов и упростить контроль остатков лекарств без бумаги и разрозненных напоминаний в календаре.

## 2. Обзор продукта {#2-product-overview}

### 2.1 Перспектива продукта {#21-product-perspective}

Medora — новый самостоятельный веб-продукт (не замена унаследованной системы). Клиентская часть работает в браузере; серверная часть хранит данные пользователя и формирует расписание/уведомления. Внешние зависимости MVP: СУБД, почтовый или push-канал для напоминаний (опционально). Владелец продукта — учебный проект в рамках дисциплины; SLA промышленного уровня не требуется, но целевые показатели доступности заданы в 3.3.4.

### 2.2 Функции продукта {#22-product-functions}

1. Управление профилем и аутентификация.
2. Ведение списка лекарств пользователя.
3. Настройка расписания приёма.
4. Ежедневный обзор запланированных доз и отметка «принято» / «пропущено».
5. Напоминания о предстоящем приёме.
6. Уведомления о пропущенных дозах.
7. Учёт и корректировка остатков препаратов.
8. Просмотр и фильтрация истории приёма.
9. Просмотр карточки лекарства (дозировка, остаток, связанные приёмы).
10. Режим опекуна (делегированный просмотр и уведомления о пропусках).

### 2.3 Ограничения продукта {#23-product-constraints}

- Система **должна** быть реализована как web-приложение.
- Серверная часть **должна** использовать язык Java (рекомендуемый стек: Spring Boot).
- Данные **должны** храниться в реляционной СУБД (рекомендуется PostgreSQL).
- Клиентский UI **должен** быть адаптивным для экранов от 360 px по ширине.
- Система **не должна** ставить медицинские диагнозы и менять дозировки без явного действия пользователя.
- Интерфейс MVP **должен** поддерживать русский язык.

### 2.4 Характеристики пользователей {#24-user-characteristics}

| Класс | Описание | Частота | Навыки |
|-------|----------|---------|--------|
| Пациент / пользователь | Ведёт личный учёт приёма лекарств | Ежедневно (несколько раз) | Базовая работа с браузером |
| Гость | Неавторизованный посетитель | Редко | Может видеть лендинг/описание, без доступа к данным |

Особые потребности: крупные элементы управления для отметки приёма «в один клик»; понятные тексты ошибок; отсутствие медицинской терминологии сверх необходимого.

### 2.5 Допущения и зависимости {#25-assumptions-and-dependencies}

**Допущения:**
- у пользователя есть стабильный доступ к интернету во время работы с приложением;
- пользователь корректно указывает дозировки и остатки (система не валидирует клиническую правильность);
- браузер поддерживает современные стандарты (Chromium / Firefox / Safari последних двух мажорных версий).

**Зависимости:**
- Java 17+, Spring Boot, СУБД PostgreSQL;
- при push-уведомлениях — поддержка Web Push API браузером и разрешение пользователя;
- хостинг/сервер для развёртывания (локально или облако).

Если допущение об интернет-доступе неверно, офлайн-режим не гарантируется в MVP (риск: пропуск напоминаний).

## 3. Требования {#3-requirements}

Формат ID: `REQ-[AREA]-[NNN]`, где AREA ∈ {FUNC, INT, PERF, SEC, REL, AVAIL, OBS, COMP, INST, BUILD, DIST, MAINT, REUSE, PORT, COST, DEAD, POC, CM}.

### 3.1 Внешние интерфейсы {#31-external-interfaces}

#### 3.1.1 Пользовательские интерфейсы {#311-user-interfaces}

**ID:** REQ-INT-001  
**Title:** Главный экран «Сегодня»  
**Statement:** Система должна предоставлять главный экран с расписанием приёмов на текущий день, блоком напоминаний/уведомлений, сводкой остатков и краткой историей недавних приёмов.  
**Rationale:** Пользователю нужен единый обзор дня без перехода по множеству страниц.  
**Acceptance Criteria:** На экране отображаются все запланированные на сегодня дозы со статусом (ожидается / принято / пропущено); доступны переходы к списку лекарств и карточке препарата.  
**Verification Method:** Demonstration

**ID:** REQ-INT-002  
**Title:** Экран карточки лекарства  
**Statement:** Система должна предоставлять экран карточки лекарства с информацией о препарате, редактированием расписания, учётом остатка, историей приёма данного препарата и действиями (отметить приём, пополнить остаток).  
**Rationale:** Детальная работа с одним препаратом.  
**Acceptance Criteria:** Все перечисленные блоки доступны; изменения сохраняются и отражаются на главном экране.  
**Verification Method:** Demonstration

**ID:** REQ-INT-003  
**Title:** Адаптивность и локализация  
**Statement:** UI должен корректно отображаться на ширине viewport от 360 px и использовать русский язык в MVP.  
**Acceptance Criteria:** Нет горизонтальной прокрутки критичных экранов на 360 px; все пользовательские строки на русском.  
**Verification Method:** Test

Структура экранов описана диаграммами SysML v2 (см. приложение к отчёту и `docs/sysml/`).

#### 3.1.2 Аппаратные интерфейсы {#312-hardware-interfaces}

Специальные аппаратные интерфейсы не требуются. Система работает на стандартных ПК, ноутбуках и мобильных устройствах через браузер.

#### 3.1.3 Программные интерфейсы {#313-software-interfaces}

**ID:** REQ-INT-010  
**Title:** REST API сервера  
**Statement:** Серверная часть должна предоставлять REST API для операций с пользователем, лекарствами, расписанием, приёмами, остатками и уведомлениями.  
**Acceptance Criteria:** Основные ресурсы доступны по HTTP; ошибки возвращаются с понятными кодами (4xx/5xx) и телом сообщения.  
**Verification Method:** Test

**ID:** REQ-INT-011  
**Title:** СУБД  
**Statement:** Система должна использовать реляционную СУБД для хранения учётных данных, расписания, истории и остатков.  
**Verification Method:** Inspection

### 3.2 Функциональные требования {#32-functional}

**ID:** REQ-FUNC-001  
**Title:** Регистрация и вход  
**Statement:** Система должна позволять пользователю зарегистрироваться (email + пароль) и выполнять вход/выход.  
**Rationale:** Персональные данные о здоровье требуют разграничения доступа.  
**Acceptance Criteria:** Успешная регистрация создаёт учётную запись; неверный пароль отклоняется; выход завершает сессию.  
**Verification Method:** Test

**ID:** REQ-FUNC-002  
**Title:** Управление списком лекарств  
**Statement:** Система должна позволять добавлять, редактировать и удалять лекарства пользователя (название, дозировка, единица измерения, форма выпуска — опционально).  
**Acceptance Criteria:** CRUD выполняется только для владельца записи; удалённое лекарство не отображается в активном расписании.  
**Verification Method:** Test

**ID:** REQ-FUNC-003  
**Title:** Расписание приёма  
**Statement:** Система должна позволять задавать для лекарства расписание: время(а) приёма, дни недели или интервал, длительность курса (опционально).  
**Acceptance Criteria:** На основе правил формируются запланированные дозы на календарный день; изменение расписания влияет на будущие дозы.  
**Verification Method:** Test

**ID:** REQ-FUNC-004  
**Title:** Отметка приёма  
**Statement:** Система должна позволять пользователю отметить дозу как «принята» или «пропущена» с фиксацией времени события.  
**Acceptance Criteria:** Статус дозы меняется; событие появляется в истории; при «принята» остаток уменьшается на размер дозы (если учёт остатков включён).  
**Verification Method:** Test

**ID:** REQ-FUNC-005  
**Title:** Напоминания о приёме  
**Priority:** 20  
**Statement:** Система должна формировать напоминания о предстоящем приёме не позднее заданного пользователем смещения до времени дозы (по умолчанию 5 минут). В MVP канал доставки — UI и опционально Web Push; email/SMS не требуются.  
**Acceptance Criteria:** Напоминание отображается в UI; при разрешении браузера может быть показано системное уведомление.  
**Verification Method:** Demonstration

**ID:** REQ-FUNC-006  
**Title:** Уведомления о пропущенных дозах  
**Statement:** Система должна помечать дозу как пропущенную, если подтверждение не получено в течение настраиваемого окна после планового времени (по умолчанию 30 минут), и уведомлять пользователя.  
**Acceptance Criteria:** Статус «пропущено» виден на главном экране и в истории; уведомление создаётся однократно на дозу.  
**Verification Method:** Test

**ID:** REQ-FUNC-007  
**Title:** Учёт остатков  
**Statement:** Система должна хранить текущий остаток препарата, позволять ручное пополнение и предупреждать, когда остаток меньше или равен порогу пользователя.  
**Acceptance Criteria:** Порог настраивается; при низком остатке отображается предупреждение на главном экране и в карточке лекарства.  
**Verification Method:** Test

**ID:** REQ-FUNC-008  
**Title:** История приёма  
**Statement:** Система должна предоставлять историю приёмов с фильтрами по периоду, лекарству и статусу (принято/пропущено).  
**Acceptance Criteria:** История содержит дату/время, препарат, дозу и статус; фильтры сужают список корректно.  
**Verification Method:** Test

**ID:** REQ-FUNC-009  
**Title:** Изоляция данных  
**Statement:** Система должна обеспечивать доступ пользователя только к своим лекарствам, расписанию, остаткам и истории, за исключением явно делегированного доступа опекуна.  
**Acceptance Criteria:** Запрос чужого ресурса по ID без активной связи опекуна возвращает 403 или 404 без утечки данных.  
**Verification Method:** Test

**ID:** REQ-FUNC-010  
**Title:** Режим опекуна  
**Priority:** 10  
**Statement:** Система должна позволять владельцу данных пригласить опекуна, а опекуну — просматривать расписание подопечного на текущий день и получать уведомления о пропущенных дозах в пределах выданных прав.  
**Rationale:** Согласовано во втором раунде обсуждения с заказчиком (ЛР4) для контроля режима приёма у пожилых родственников без сдвига дедлайна MVP.  
**Acceptance Criteria:**  
- владелец создаёт и отзывает приглашение;  
- опекун после принятия видит только разрешённые данные подопечного;  
- уведомление о пропуске доставляется опекуну при активной связи;  
- отзыв связи немедленно закрывает доступ.  
**Verification Method:** Test

### 3.3 Качество обслуживания {#33-quality-of-service}

#### 3.3.1 Производительность {#331-performance}

**ID:** REQ-PERF-001  
**Title:** Время отклика UI-операций  
**Statement:** При типичной нагрузке MVP (до 100 одновременных пользователей) основные операции (открытие главного экрана, отметка приёма) должны завершаться не более чем за 2 секунды при нормальном сетевом RTT.  
**Verification Method:** Test

#### 3.3.2 Безопасность {#332-security}

**ID:** REQ-SEC-001  
**Title:** Хранение паролей  
**Statement:** Система должна хранить пароли только в виде криптографического хеша (например, BCrypt), а не в открытом виде.  
**Verification Method:** Inspection

**ID:** REQ-SEC-002  
**Title:** Защита канала  
**Statement:** В развёрнутом окружении обмен между клиентом и сервером должен выполняться по HTTPS.  
**Verification Method:** Inspection

**ID:** REQ-SEC-003  
**Title:** Авторизация API  
**Statement:** Все операции с персональными данными должны требовать аутентифицированную сессию или токен.  
**Verification Method:** Test

#### 3.3.3 Надёжность {#333-reliability}

**ID:** REQ-REL-001  
**Title:** Сохранность отметок  
**Statement:** Успешно подтверждённая отметка приёма должна сохраняться в БД и не теряться при последующем обновлении страницы.  
**Verification Method:** Test

**ID:** REQ-REL-002  
**Title:** Идемпотентность повторной отметки  
**Statement:** Повторная отметка уже обработанной дозы не должна повторно уменьшать остаток.  
**Verification Method:** Test

#### 3.3.4 Доступность {#334-availability}

**ID:** REQ-AVAIL-001  
**Title:** Целевая доступность учебного стенда  
**Statement:** Для учебного развёртывания целевая доступность сервиса — не ниже 95% в течение демонстрационного периода (исключая плановые окна обслуживания).  
**Verification Method:** Analysis

#### 3.3.5 Наблюдаемость {#335-observability}

**ID:** REQ-OBS-001  
**Title:** Журналирование ошибок  
**Statement:** Сервер должен журналировать ошибки уровня ERROR с меткой времени и идентификатором запроса без записи паролей и токенов в открытом виде.  
**Verification Method:** Inspection

### 3.4 Соответствие стандартам {#34-compliance}

**ID:** REQ-COMP-001  
**Title:** Ограничение медицинской ответственности  
**Statement:** Система должна явно информировать пользователя (в UI или справке), что Medora не является медицинским изделием и не заменяет консультацию врача.  
**Verification Method:** Inspection

**ID:** REQ-COMP-002  
**Title:** Персональные данные  
**Statement:** Обработка учётных данных пользователя должна ограничиваться целями работы приложения; в MVP экспорт/удаление аккаунта по запросу пользователя должно быть предусмотрено как минимум через обращение к администратору стенда или через функцию удаления аккаунта.  
**Verification Method:** Demonstration

### 3.5 Проектирование и реализация {#35-design-and-implementation}

#### 3.5.1 Установка {#351-installation}

**ID:** REQ-INST-001  
**Title:** Локальный запуск  
**Statement:** Проект должен иметь инструкцию по запуску (README): требования к JDK, СУБД, переменные окружения, команды старта backend и frontend.  
**Verification Method:** Inspection

#### 3.5.2 Сборка и поставка {#352-build-and-delivery}

**ID:** REQ-BUILD-001  
**Title:** Сборка backend  
**Statement:** Backend на Java должен собираться стандартным инструментом сборки (Maven или Gradle) одной командой.  
**Verification Method:** Demonstration

#### 3.5.3 Распределение {#353-distribution}

MVP предполагает одноузловое развёртывание (один сервер приложений + СУБД). Геораспределение не требуется.

#### 3.5.4 Сопровождаемость {#354-maintainability}

**ID:** REQ-MAINT-001  
**Title:** Модульность  
**Statement:** Код должен быть разделён на слои (как минимум: API/контроллеры, сервисы, доступ к данным) с понятной структурой пакетов.  
**Verification Method:** Inspection

#### 3.5.5 Повторное использование {#355-reusability}

Компоненты UI карточки дозы и формы лекарства должны быть пригодны к повторному использованию на главном экране и в карточке препарата.

#### 3.5.6 Переносимость {#356-portability}

**ID:** REQ-PORT-001  
**Title:** Независимость от ОС сервера  
**Statement:** Backend должен запускаться на ОС Windows и Linux при наличии совместимой JVM.  
**Verification Method:** Demonstration

#### 3.5.7 Стоимость {#357-cost}

Для учебного MVP предпочтительны бесплатные/open-source компоненты (PostgreSQL, Spring Boot). Платные внешние SMS-шлюзы в MVP не используются.

#### 3.5.8 Сроки {#358-deadline}

**ID:** REQ-DEAD-001  
**Title:** Срок ЛР3  
**Statement:** Документ SRS, две SysML-диаграммы экранов и разделы отчёта должны быть готовы к сдаче лабораторной работы №3 в установленный преподавателем срок.  
**Verification Method:** Inspection

#### 3.5.9 Доказательство концепции {#359-proof-of-concept}

PoC для MVP: демонстрация сценария «создать лекарство → задать расписание → получить напоминание → отметить приём → увидеть уменьшение остатка и запись в истории».

#### 3.5.10 Управление изменениями {#3510-change-management}

**ID:** REQ-CM-001  
**Title:** Изменения через Git  
**Statement:** Изменения SRS и диаграмм должны фиксироваться в Git; согласование — через Pull Request.  
**Verification Method:** Inspection

### 3.6 ИИ/МО {#36-aiml}

В MVP компоненты искусственного интеллекта и машинного обучения **не используются**. Раздел зарезервирован на будущее (например, прогнозирование окончания запаса).
